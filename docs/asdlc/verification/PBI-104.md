# PBI-104 — paczka danych w opisie każdego PR

**Status: w toku.** Zlecenie użytkownika 2026-10-20: każda PR-ka,
zaczynając od #12, ma publikować w swoim opisie paczkę danych taką jak
podczas eksportu wydania, aby można było sprawdzać poszczególne pliki.
To kontynuacja PR #12; [plan](../pr_data_preview_plan.md),
[kontrakt](../../release_artifacts.md#paczka-danych-w-opisie-pr).

## Zakres i architektura

`pr-data.yml` / `PR data exports` buduje dokładny syntetyczny merge PR
z bazą, po sprawdzeniu jego rodziców. Używa kanonicznego
`build_release_artifacts`, publikuje dziewięć plików release oraz
`preview.json` i `SHA256SUMS` przez `upload-artifact@v4` na 90 dni.
Etykieta podglądu: `pr-{number}-{head12}`. Manifest zachowuje head/base/merge,
run i próbę uruchomienia. Eksporty trafiają do katalogu głównego ZIP.

Osobny `publish-pr-data.yml` nasłuchuje `workflow_run` w stanach
`in_progress` i `completed`. `.github/scripts/publish_pr_data.cjs`
z zaufanej gałęzi domyślnej czyta wyłącznie metadane API GitHub i utrzymuje
blok między `<!-- pr-data-preview:start -->` / `<!-- pr-data-preview:end -->`
w opisie PR. Zachowuje ręczny tekst i odrzuca stare SHA/runy, nie wykonuje
kodu ani nie pobiera artefaktów PR. Kontroluje również metadane forka.

Dane/config/schema i surowe źródła zachowują bajty. PBI-102–103 TPN
pozostają planowane. Bez merge, tagu, release lub harmonogramu.

## Uruchomienie publishera dla pierwszego PR

Automatyczny publisher `workflow_run` wymaga obecności workflow w gałęzi
domyślnej i będzie działał po ludzkim merge. Dla #12 po odbiorze ZIP
operator uruchamia tę samą logikę lokalnie przez uwierzytelnione API
GitHub. Nie wymaga to przeglądarki ani odblokowanego systemowego okna
wyboru pliku. Dopiero wynik API i readback opisu potwierdzają publikację.

Żaden z oczekujących punktów powyżej nie jest jeszcze dowodem PASS.
Końcowy log zostanie uzupełniony rzeczywistymi wynikami i odnośnikami;
SHA końcowego commitu dokumentacji oraz jego CI może utrwalić opis PR,
bez kolejnego commitu wyłącznie dla własnego SHA.
