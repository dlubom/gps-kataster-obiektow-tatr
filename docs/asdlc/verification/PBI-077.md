Status: **planowane — gotowe**, P3 z konkretnego audytu sharda13 PBI-054.
Zależności: 045/048/062/065, wykonane. Nie rozpoczęto implementacji.
Baza produktu: `97428eb9950b0fc8bc42b137c01d6d20525e4161`.

Oryginał poprawnie rozróżnia następujące warianty, lecz aktualne regresje
pozwalają przeżyć ich zmianom (dokładne ID z jednej generacji Linux):

- `pig_staging.x_build_pig_staging__mutmut_36`: utrata podstawowej Nazwa
  i fallback do syntetycznego PIG row N mimo legalnej niepustej nazwy.
- `tpn_staging.x__load_pig_staging_candidates__mutmut_99`: usunięcie odczytu row.name
  i użycie fallbacku proposal.name_local kandydata do matching.
- `tpn_staging.x__parse_date__mutmut_7`: utrata legalnego formatu
  `YYYY-MM-DD` i użycie fallbacku zamiast dnia źródłowego.
- `tpn_staging.x_build_tpn_staging__mutmut_96`: break po wierszu bez
  GLOBALID gubi dalsze legalne wiersze zamiast ich dalszego przetworzenia.

Każdy ID ma prefix `gps_kataster_obiektow_tatr.`. Zmiany są lukami
regresji, nie dowodem błędu oryginalnego kodu. Nie przenosić statusów
starej kampanii; źródłem jest zweryfikowany shard13 oraz ukończony
pełny ledger Linux 10218 ID, 8472 killed / 1721 survived / 25 no tests.

Odbiór: publiczne in-process buildy PIG/TPN i matching przy świadomie
odrębnych row.name/name_local oraz podstawowej nazwie kontra fallback.
Data źródła tylko z dniem, datetime z offsetem, brak daty i jawny
generated_at muszą mieć literalne, niezależne oczekiwania. Wiersz bez
GLOBALID pomiędzy dwoma legalnymi: zachować rejected i wszystkie
pozostałe rows/proposals/payloady/record_number w poprawnej kolejności.
Sprawdzić dalszy review/final YAML dla zachowywanych nazw/dat.
