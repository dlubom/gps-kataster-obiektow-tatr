## Zachowanie

Użytkownik potwierdził pierwszy dzień miesiąca **03:17 UTC**
(04:17 zimą / 05:17 latem w Polsce), cron `17 3 1 * *`.
Schedule i dispatch używają tego samego prepare, blokady concurrency,
walidacji oraz publishera. Schedule nie może apply/refresh. Transfer v2
wiąże także typ zdarzenia; nie można publikować miesięcznego planu jako
ręcznego. Kod pozostaje przypięty do main, PR dostarcza wyłącznie dane.

Repozytoryjna zmienna `TPN_MONTHLY_ENABLED` musi mieć dokładną wartość true.
Brak aktywacji daje disabled bez sieci/publikacji. Jej wartości nie ustawiano.
Odczyt API repo 2026-10-21 potwierdził brak tej zmiennej,
default_workflow_permissions=read, can_approve_pull_request_reviews=false.
Nie zmieniano uprawnień, ochrony, review ani merge.

Każde aktywne prepare pobiera pełne źródło. Przy otwartym PR wykonuje
odczyt/porównanie w izolowanej kopii przyjętego main, bez commitów i apply.
Summary i artefakt z retencją 14 dni pokazują klasyfikacje, odroczenia,
requires_pr, snapshot, numer/HEAD/wiek zaległego PR. Dotychczasowy PR,
snapshot i decyzje nie są nadpisywane. No-op nie publikuje commitu/PR;
błąd API daje failure i diagnostykę również przy istniejącym PR.

Po awarii push → create PR odzyskiwany jest dokładny poprzedni HEAD;
osobna inspekcja main nadal pobiera świeże źródło. Może wskazać rewizję
nowszą od odzyskiwanej paczki, wymagającą jawnego refresh operatora.
PR pojawiający się między plan a publish zatrzymuje publikację; summary
wskazuje rzeczywisty zaległy PR zamiast nieopublikowanego kandydata.

## Pozostały odbiór i dostawa

Nie wykonywano produkcyjnego schedule, dispatch ani nowego PR przez token.
Najpierw człowiek rozpatruje/scala PR #12, zachowując wymaganą historię,
oraz osobno decyduje o wyłączonej możliwości tworzenia PR przez Actions.
Następnie rzeczywisty odbiór PBI-102 sprawdza token, pending, indywidualne
decyzje, zatwierdzanie workflow i wszystkie checki/eksporty dokładnego SHA.
Nie wymuszać zmiany danych tylko po to, by wywołać PR.

Dopiero po tym odbiorze maintainer może aktywować zmienną. Odbiór PBI-103
obejmuje rzeczywisty run miesięczny/ręczny oraz świeżość vars przy zmianie
między jobami. Test funkcji potwierdza blokadę dla przekazanego false,
nie gwarantuje odświeżenia kontekstu vars w już trwającym runie.
Do awaryjnego zatrzymania służy Cancel workflow. Runbook opisuje best-effort
GitHub, możliwe wyłączenie po 60 dniach i ręczne wznowienie.

Końcowy commit/zdalny SHA, pełne CI i świeży ZIP/readback dokładnego HEAD
utrwala opis PR #12; bez kolejnego commitu wyłącznie dla własnego SHA.
Do rzeczywistego odbioru status nie jest „wykonane”. Bez merge, tagu,
release, ustawienia zmiennej lub uprawnień Actions. Nie rozpoczynać
kolejnej karty.
